1. Executive Summary
NDCAK Digital Tournament Management System is a centralized web platform for operating the full lifecycle
of an NDCAK indoor games event. It combines a public event website, a one-time participant registration and
manual payment verification flow, a Super Admin control center, and a restricted Score Operator workspace
for game-wise / participant-wise result entry.
The product is not a generic esports portal and should not look or behave like one. The public side should feel
like a modern university-association event website: clean, credible, energetic, responsive and easy to
understand. Staff dashboards should be operational tools first: information-dense where necessary, but
restrained, legible and task-focused.




                                       Figure 1. System context and major external services.

Core product rule
 Keep participant interaction simple
 A participant selects every desired game during the initial registration form, reviews details, submits payment information once,
 and waits for admin verification. There is no participant account, no later game-registration phase, and no tournament-
 management dashboard for participants.



Core operational rule
A game can contain many participants, many rounds and many matches, and multiple operators may work on the
same game. One operator can also be assigned to multiple games. Admin assignment must be flexible enough to
grant an operator access to the whole tournament, one or more games, selected rounds, selected matches, or
selected participant entries.


2. Product Vision, Objectives and Non-Goals
2.1 Vision
Replace fragmented forms, spreadsheets, manual messaging and ad-hoc score tracking with a single trusted
tournament operations platform that is simple for students and controlled for organizers.

2.2 Product objectives
 • Provide a polished public event website with event information, schedule, rules, prizes and registration.
 • Allow a student to register for multiple eligible game segments in one straightforward flow.
 • Capture payment method and transaction ID, then keep the request pending until manual Super Admin verification.
 • Give Super Admin full visibility into registrations, payment status, games, participants, operators, assignments,
   matches, score activity and analytics.
 • Allow Super Admin to create operator accounts and assign flexible scopes without exposing unrelated
    participant/payment data.
 • Provide game-specific score-entry experiences rather than forcing every game into one Player A / Player B numeric
    format.
 • Support matches with two or more competitors; the data model must not hardcode exactly two players.
 • Update Super Admin views near real time as operators submit results.
 • Preserve an audit trail for sensitive actions and score/result changes.
 • Remain responsive, fast and usable on mobile, tablet and desktop using free-tier infrastructure for the expected event
   scale.

3.1 Participant experience boundary
 • One registration journey only: form -> review -> payment information -> submitted/pending -> email after decision.
 • Game selection happens inside the initial form. Selected game entries are created automatically in the backend.
 • No additional action is required after submission unless an organizer contacts the participant following
   rejection/problem.
 • The same generated registration code can remain the stable identifier from submission through approval. It is valid for
    check-in only when registration status is CONFIRMED.
 • Participants should never see internal operator assignment, audit logs, payment verification controls, internal notes or
    unpublished results.

3.2 Operator experience boundary
 • Operator accounts are created/deactivated by Super Admin; there is no public operator signup.
 • Operator navigation is generated from effective permissions, not from a hardcoded single-game role.
 • Operators see only minimum participant identity needed for match operations (for example name, registration
   code/student ID if required, assigned game and match context).
 • Operators do not see payment method, transaction ID, personal phone/email unless a specific operational requirement
   is later approved.
 • Completed/finalized result correction is controlled; normal operators cannot silently rewrite historical results.

3.3 Super Admin experience boundary
 • All critical configuration and staff management lives under the Super Admin area.
 • Admin can override tournament state when necessary, but every override must produce an audit event.
 • Admin tables must use search/filter/pagination and must not depend on loading the entire dataset into the browser.
 • Admin must be able to reassign work quickly on event day without editing database records manually.

4.3 UI principles
 • Clarity over decoration: every visible element should help orientation, decision-making or action.
 • Consistent spacing: use an 8px base spacing rhythm and a constrained container width on public pages.
 • Primary action should be visually obvious; do not place multiple equally loud CTAs together.
 • Use icons as support, not as replacements for clear labels.
 • Do not use emojis as production UI icons. Use Lucide or purpose-built SVG icons.
 • Avoid giant all-caps blocks in forms/admin pages. Reserve condensed uppercase typography for event display
    moments.
 • No random gradients, glows, neon lime, oversized statistic walls, or decorative cards just because space exists.
 • Use real event/game imagery only where it improves the public story. Use licensed/free-to-use images, optimize them,
   and avoid imagery in operational dashboards unless necessary.

4.4 Responsive behavior
 • Public pages are mobile-first. Registration must be effortless on common phones.
 • Operator dashboard is mobile/tablet-first because staff may move around the venue.
 • Admin dashboard is desktop-optimized but must remain usable on tablet/mobile. Dense tables may become stacked
    cards or horizontally scrollable views with key columns preserved.
 • No layout should depend on hover-only interactions.
 • Touch targets should be at least approximately 44x44 CSS pixels for important controls.

The game-selection section must clearly show each game’s fee and remaining capacity. The total fee updates
immediately as selections change. All calculations are repeated server-side; client totals are never trusted.

6.2 Review step (P0)
 • Display all participant fields, selected games, per-game fee where useful, and total expected payment.
 • Provide a single Back/Edit action and a single Proceed to Payment primary action.
 • No database confirmation occurs merely because the user reached the review page.

6.3 Payment submission (P0)
 • Admin configures enabled payment methods (for example bKash, Nagad, Rocket), display name, receiving
    account/number and instructions.
 • Participant selects one method, sends payment outside the website, then enters the transaction ID/reference.
 • System records expected amount, selected payment method, a snapshot of the receiving number/account shown at
    submission, and normalized transaction ID.
 • Transaction ID should be normalized (trim/case normalization) and checked for duplicate use within the same provider.
    Duplicate detection should block or flag submission rather than silently accepting it.
 • V1 does not request a payment screenshot and does not integrate a payment gateway/API unless the committee later
    changes scope.

6.4 Atomic submission and slot reservation
Final submission must be transactional. The server rechecks registration window, per-person selection limit, game
status and capacity. It then creates the participant/registration records, pending game entries, payment submission
and pending slot reservations in one database transaction. If any required game no longer has capacity, nothing is
partially created and the user is asked to revisit selection.
 BEGIN
   validate registration window and input
   upsert/create participant identity
   create registration(status=PENDING_REVIEW)
   create registration_game_entries(status=PENDING)
   reserve capacity for each selected game
   create payment(status=SUBMITTED)
   write audit/system event
 COMMIT



6.5 Submission response
 • Generate a human-readable registration code such as REG-2026-000147. Use the same code through pending and
   confirmed states to avoid confusing participants with multiple identifiers.
 • Show “Registration Submitted” / “Pending Verification”, never “Registration Confirmed” before admin approval.
 • Send a submission acknowledgment email with registration code, selected games, expected amount/payment
    reference summary, and a clear statement that approval is pending.
 • Do NOT attach the final calendar invite at this stage; send it after approval.

7. Super Admin Registration Review
7.1 Pending approval queue
Pending registrations are a dedicated operational queue, not merely a status column in a giant table. Default view
should show oldest pending submissions first or allow sorting.
 Capability                                                      Requirement
 Search                                                          Name, student ID, registration code, email or transaction ID.
 Filters                                                         Status, game, department, payment method, submission date
                                                                 range.
 Sorting                                                         Submitted time, name, amount; default oldest pending first.
 Pagination                                                      Server-side, default 25 rows/page; preserve query filters in URL.
 Quick status tabs                                               Pending, Confirmed, Rejected, All.
 Review action                                                   Open focused detail page/drawer without losing list filters.



7.2 Registration review detail
 • Participant identity: name, student ID, department/year, email, phone.
 • Selected games and expected fee calculation.
 • Payment method, receiving account/number snapshot, expected amount, transaction ID and submission timestamp.
 • Registration status and audit timeline.
 • Approve and Reject actions. Reject requires a reason; optional internal note is allowed.
 • Admin manually checks the transaction in the corresponding external payment service before approval.

7.3 Approval transaction
Approval must be idempotent and transactional. A double click or repeated request must not allocate slots twice or
send duplicate state changes.
 BEGIN
   lock/read registration and verify status=PENDING_REVIEW
   verify pending game-entry reservations still valid
   payment.status = VERIFIED
   registration.status = CONFIRMED
   each registration_game_entry.status = CONFIRMED
   finalize reserved slots
   write audit log(actor=admin, action=REGISTRATION_APPROVED)
 COMMIT

 after commit: send approval email + .ics; record notification result



7.4 Rejection transaction
 • Rejection reason is required and stored.
 • Registration and payment states change to rejected, pending game entries are rejected, and reserved capacity is
   released atomically.
 • Rejection email includes a participant-safe reason. Internal notes are never sent.
 • Old rejected records remain available for audit/history. A participant may submit a new registration later if registration is
   still open and policy permits; duplicate rules must ignore rejected historical attempts where appropriate.

8.2 Game configuration
 • Admin can enable/disable a game for registration.
 • Per game: capacity, fee, rules, registration open flag, tournament format, progression mode and scoring adapter.
 • Maximum games per participant is a tournament-level configuration, not hardcoded to any number.
 • Each tournament game may use AUTOMATIC progression or MANUAL progression. This is important for
    custom/multi-player formats such as card games where a standard 1v1 bracket may not fit.

8.3 Capacity semantics
 • Capacity should count confirmed + pending reserved entries unless the committee chooses a different policy.
 • Rejected/cancelled entries release capacity immediately.
 • Capacity checks must happen inside database transactions to prevent race-condition oversubscription.
 • Admin may increase/decrease capacity, but the system must block decreasing below current reserved/confirmed count
    unless an explicit override workflow is implemented.

10.1 Match model must support N competitors
 Do not model matches as player_1_id + player_2_id
 Chess/FIFA may be 1v1, but the system requirement explicitly allows multiple players in a game/match. Use a match_entries
 junction table so a match can contain 2, 3, 4 or more competitors.

10.3 Game-specific scoring adapters
Implement a TypeScript scoring-adapter interface. Each tournament game references an adapter key. The UI and
server share adapter-specific validation, while the database stores canonical result/placement output plus
structured JSON for game-specific details.

10.5 Finalization rules
 • Server verifies operator effective access at request time; UI visibility is not authorization.
 • Server validates match status and expected record version before applying updates.
 • Final result is written in a database transaction with canonical placements, match status, progression updates and
    audit log.

11. Tournament Progression and Results
11.1 Progression modes
 Mode                                                          Behavior
 AUTOMATIC_SINGLE_ELIMINATION                                  On finalization, winning/qualifying entry is inserted into the
                                                               configured next match/round slot.
 MANUAL                                                        Result is stored, but admin chooses/creates the next-round
                                                               competitors. Useful for custom multi-player/card formats.
 FUTURE: ROUND_ROBIN / GROUP                                   Data model may support later; not required to block V1.



11.2 Bracket / round generation
 • Admin can generate or manually create rounds/matches after registration closes or when participant list is ready.
 • Seeding strategy can be random/manual in V1. Do not claim advanced ranking seeding unless implemented.
 • Bracket generation must operate on CONFIRMED registration_game_entries only.
 • Byes and uneven participant counts must be supported for single elimination.
 • Admin can edit schedule/venue/table metadata without altering result history.

11.3 Multi-event awards / cross-game points
The platform may calculate tournament-wide awards such as highest cumulative points or most game segments.
Award rules must be configurable rather than embedded in UI. For example, the committee may configure
champion=3 points and runner-up=1 point. Calculations derive from finalized game placements only.
 • Never calculate awards from in-progress scores.
 • Tie-break policy must be explicit/configurable (for example number of wins, then runner-up finishes, then admin
    decision).
 • Admin can view the computed leaderboard. Public visibility is a separate setting.

18. Authorization, Security, Concurrency and
Auditability
18.1 Authorization model
Use RBAC for coarse role (SUPER_ADMIN vs SCORE_OPERATOR) plus resource-based assignment checks for
operators. This is effectively RBAC + ABAC/resource scopes.
 canOperatorAccessMatch(operatorId, matchId, capability):
   return active assignment exists where
     scope == ALL_TOURNAMENT
     OR scope game == match.tournament_game_id
     OR scope round == match.round_id
     OR scope match == match.id
     OR scope participant_entry intersects match.entries
   AND assignment grants capability


 • Every server mutation repeats authorization. Never rely on hidden buttons/client route guards only.
 • Super Admin bypasses operator scope checks but still generates audit events.
 • Any client-side Supabase Realtime subscription should use authenticated channels/RLS as appropriate; do not expose
    privileged write access to the browser.

18.2 Security controls
 • Zod validation on server for every external input.
 • Cloudflare Turnstile or equivalent anti-bot/rate limiting on public registration submission (recommended P0/P1).
 • Rate limit repeated registration attempts and staff login endpoints using platform-appropriate controls.
 • Use secure, HTTP-only auth cookies/session handling supplied by Supabase/Next integration.
 • Keep DB URLs, service-role key and Resend key server-only.
 • Escape/render participant-entered data safely; never inject into HTML emails without templating/escaping.
 • No sensitive values in application logs. Transaction IDs may be logged only in protected structured audit where
   needed, not console traces.
 • Admin/operator routes should be noindex and require auth on the server.

18.3 Concurrency
 • Registration approval/rejection uses row/state checks so the same request cannot be processed twice.
 • Match record has integer version. Operator opens version N; update succeeds only if current version is still N, then
   increments to N+1.
 • If version conflict occurs, return 409-style conflict and ask the operator to reload current match state rather than
    overwriting.
 • Optional P1: show staff presence/“being edited by” hint, but correctness must not depend on a UI lock.

18.4 Audit requirements
 • Audit registration approved/rejected/cancelled, payment status changes, operator account create/deactivate,
    assignment add/revoke, match finalize/reopen/correct, game configuration changes and manual progression
    overrides.
 • Audit records are append-only to application users; do not offer a normal “delete audit record” UI.
 • For corrections, store a reason and meaningful before/after snapshot.

25. Acceptance Criteria
